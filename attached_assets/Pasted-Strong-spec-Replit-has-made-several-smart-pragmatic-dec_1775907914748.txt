Strong spec. Replit has made several smart pragmatic decisions that improve on the original prompt. Here's the honest evaluation:
What Replit got right
The HITL token system as a standalone DB table is a better architectural decision than relying on Add-on 3's file-based /hitl-decisions/ store. A separate hitl_tokens table with onboarding_request_id and phase fields means the orchestrator can query HITL state directly from the DB rather than polling the filesystem, which matters when the workflow spans hours or days across two approval gates. The POST /api/hitl/respond/:token pattern is also cleaner than the email link approach — approvals happen in-dashboard without Resend dependency, which is the right call given Resend isn't yet confirmed as live.
Scoping the sandbox eval to 5 scenarios rather than 20 is correct for onboarding. The candidate files don't yet have 30 days of Witness log history to draw realistic scenarios from — 5 well-constructed governance scenarios against the candidate SOP.md is proportionate and honest about what the eval can actually validate at this stage.
The GitHub PR being optional (if GITHUB_TOKEN is set) with VC issuance and Agent Card registration proceeding regardless is pragmatic. It means the system works in development without GitHub credentials configured, and the production commit path activates cleanly when the token is present.
The self-onboarding guard at the A2A handler level (if agent_card.name === "onboarding-agent" return -32006 immediately) is correctly placed — it fires before the orchestrator is even called, which is the right enforcement layer.
Seeding the Onboarding Agent's own governance files via seed.ts on first start is the correct pattern — it means the agent's governance envelope exists before any request arrives, satisfying the §2.1 Enforcement Rule for the agent that enforces §2.1 on everyone else. That's the self-referential property working correctly.
Two things to watch in implementation
The Impact Delta Analyser is specified as deterministic — no Claude API, string matching only against governance file content. This is correct and important. However the MAY clause detection depends on parsing SOP.md files for unexercised permissions by comparing against witness_entries.clause_applied. This works well for agents that have been running for weeks, but for a fresh installation with minimal Witness log history the friction detection will return sparse results. Worth a note in the README: "Impact delta friction analysis becomes more accurate as the Witness log accumulates operational history."
The orchestrator phase transitions are triggered by POST /api/hitl/respond/:token updating the record and then calling "next orchestrator phase." The spec doesn't define how that trigger works mechanically — whether it's a direct function call, an event, or a polling loop. This needs to be explicit in implementation: the cleanest approach is a direct function call from the respond endpoint into the orchestrator with the onboarding_request_id, rather than polling the DB for status changes. Polling introduces race conditions if two HITL responses arrive close together.
One gap relative to your original requirement
The RACI exception notification — where both candidate owners are informed when a cross-domain intersection has no clear single owner — is in your prompt but absent from Replit's spec. The spec covers RACI exceptions in the Impact Delta Report output but doesn't define how both owners are notified. Given Resend is out of scope, this should be handled as a second pending HITL card in the dashboard HITL Approvals sub-tab, not an email. Worth adding explicitly to the dashboard spec: RACI exception cards appear as informational (no approve/reject) with both owner names shown, so the Compliance Officer knows who to contact.
Verdict
Implement as written with one addition: define the phase transition trigger mechanism explicitly as a direct function call from POST /api/hitl/respond/:token into the orchestrator. Everything else is production-ready. The scope decisions Replit made — dropping Resend, capping eval at 5 scenarios, making GitHub optional — are all correct calls that make this implementable without blocking dependencies.
