You are extending the Witness Agent audit system in the VDA-MD Framework 
running on Replit. The Witness Agent currently records agent decisions 
(PASS/FAIL/ESCALATE) to the witness_entries table. This task extends it 
to record everything that affects how agents are allowed to behave — not 
just the decisions agents make, but the governance changes, framework 
integrity events, lifecycle transitions, and compliance boundary crossings 
that determine what agents are permitted to do in the first place.

The following are already built and live:
- witness_entries table with: id, company_id, agent_id, decision, 
  clause_applied, governance_file, files_consulted, escalation_target,
  apaleo_data, credential_verified, governance_file_hash, created_at
- Compliance Guard: rejects governance file saves that reduce MUST counts,
  remove NIST references, or delete ISO 42001 citations (returns 409 Conflict)
- W3C VC layer: 23-hour rotation, governance file hash binding, 
  credential_verified and governance_file_hash already in witness_entries
- A2A Protocol: JSON-RPC 2.0, Agent Card registry, a2a_tasks table,
  event_types a2a_task_received/completed/failed/cancelled/session_started
  already written to witness_entries
- Onboarding Agent: 7-phase orchestration, onboarding_requests table,
  agent_onboarded/agent_offboarded/impact_delta_complete etc already 
  written to witness_entries
- ESM api-server, PostgreSQL via Drizzle ORM

THIS TASK: Add an event_category field to witness_entries and ensure every 
system component writes categorised, structured Witness entries for all 
events that affect agent behaviour. No existing Witness entry format changes.
All additions are additive.

2. UPDATED writeWitnessEntry FUNCTION

   The existing writeWitnessEntry function in agents.ts accepts a 
   WitnessEntryInput interface. Add event_category as an optional field
   to WitnessEntryInput (optional for backwards compatibility — existing
   callers do not break).

   Create a new strict variant: writeGovernanceEvent() in 
   artifacts/api-server/src/lib/witnessGovernanceEvents.ts

   writeGovernanceEvent requires event_category — it will not compile 
   without it. This is the function all new Witness entries in this task
   use. Existing agent decision entries continue using writeWitnessEntry.

   writeGovernanceEvent signature:
   writeGovernanceEvent({
     event_category: WitnessCategory,  // required
     event_type: string,               // required — specific event name
     company_id: number,               // required
     agent_id: string,                 // required
     decision: "PASS" | "FAIL" | "ESCALATE" | "INFO",  // INFO is new
     details: Record<string, unknown>, // required — all event-specific fields
                                       // stored in existing apaleo_data jsonb
     governance_file?: string,
     credential_verified?: boolean,
     governance_file_hash?: string
   })

   INFO is a new decision value — add it to the decision column's 
   accepted values via a DB migration. INFO is used for events that 
   are not agent decisions but must be recorded (lifecycle events, 
   integrity checks, data governance). It does not trigger escalation.

4. GOVERNANCE FILE HASH VERIFICATION JOB
   (artifacts/api-server/src/lib/governanceIntegrityCheck.ts)

   Create a scheduled job using node-cron that runs every 6 hours.
   For every governance file in the DB:
   - Recompute SHA-256 of current content
   - Compare against the governance_file_hash stored in the most 
     recent VC for that (companyId, agentId) pair
   - If match: write INFO entry, event_type: "integrity_check_passed"
   - If mismatch: write FAIL entry, event_type: "integrity_check_failed",
     decision: "ESCALATE", details include: file, stored_hash, 
     computed_hash, last_vc_issued_at
   
   A mismatch means a governance file was changed outside the normal 
   PR/approval flow — this is the highest severity framework integrity 
   event. The ESCALATE decision routes to the file's owner field from 
   YAML front matter.

   Import and start this scheduler from the api-server main entry point
   alongside the existing credential rotation scheduler.
