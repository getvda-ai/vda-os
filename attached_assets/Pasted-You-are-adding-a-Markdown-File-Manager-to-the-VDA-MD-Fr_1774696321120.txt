You are adding a Markdown File Manager to the VDA-MD Framework. This is both a 
tab inside the existing React app (vdamd-templateV2.jsx) AND a Node.js/Express 
backend service running in the same Replit project.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
WHAT THIS IS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

A full CRUD Markdown file manager with invisible Git version control baked in.
Every file in the VDA-MD framework — AGENTS.md, SOP.md, SKILL.md, EXCEPTION.md,
C2MD compliance files, A2MD normalised passports — lives here. The manager is 
also itself an AI agent (the FM Agent) that monitors, suggests, and automates.

Core axiom: every save is a Git commit. Every owner approval is a Git tag. 
Every release is a Git release. The user never sees Git — they see governance 
workflow. Git is invisible infrastructure.

BACKEND — server.js (Express + simple-git)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FILE SYSTEM STRUCTURE:

  /governance/
    /[company-slug]/
      /[industry]/
        /journey/
          /[stage-id]/
            agents.md
            sop.md
            skill.md
            exception.md
        /shared/
          /[service-id]/
            agents.md
            sop.md
            exception.md
        /compliance/
          ac-2.md
          au-2.md
          [control-id].md
      /releases/
        [tag].md       ← auto-generated release notes

  /governance/.git/    ← Git repo, hidden from user

On first run, initialise a Git repo in /governance/ if none exists:
  git.init()
  git.addConfig('user.name', 'VDA-MD File Manager')
  git.addConfig('user.email', 'filemanager@vdamd.local')

BACKEND API ROUTES:

POST /api/fm/init
  Body: { companySlug, industry }
  Creates the directory structure above
  Runs git init if needed
  Returns: { success, path }

GET /api/fm/files/:companySlug
  Returns all .md files as a tree with metadata:
  [
    {
      id: uuid,
      path: "journey/arrive/agents.md",
      filename: "agents.md",
      type: "AGENTS" | "SOP" | "SKILL" | "EXCEPTION" | "COMPLIANCE" | "RELEASE",
      axis: "vertical" | "horizontal" | "compliance",
      stage: stage id or service id,
      owner: from YAML front matter,
      domain: from YAML front matter,
      status: "draft" | "review" | "live" | "expired",
      expiresAt: date or null (from YAML front matter),
      lastModified: timestamp,
      commitHash: latest git commit hash for this file,
      isExpired: boolean,
      expiresInDays: number or null,
      wordCount: number,
      clauseCount: { must: n, mustNot: n, may: n },
      signedBy: from YAML front matter or null,
      signedAt: from YAML front matter or null,
    }
  ]

GET /api/fm/file/:companySlug/*
  Returns full file content + metadata + git history for one file
  gitHistory: last 20 commits for this file
  [
    { hash, message, author, date, diff }
  ]

POST /api/fm/file/:companySlug/*
  Body: { content, message, author }
  Writes file to disk
  Runs: git add [file] && git commit -m "[message]"
  Auto-generates commit message if none provided:
    "Update [filename] — [clauseCount] clauses, owner: [owner]"
  Returns: { success, commitHash, path }

POST /api/fm/sign/:companySlug/*
  Body: { signerName, signerRole }
  Adds to YAML front matter:
    signed_by: [signerName]
    signed_role: [signerRole]
    signed_at: [ISO timestamp]
    status: live
  Commits: "✓ Owner sign-off: [filename] approved by [signerName]"
  Creates a Git tag: "signed/[filename-slug]/[timestamp]"
  Returns: { success, commitHash, tag }

DELETE /api/fm/file/:companySlug/*
  Moves file to /governance/[company]/_archive/[filename]-[timestamp].md
  (Never hard-deletes — archive only)
  Commits: "Archive [filename]"
  Returns: { success }

GET /api/fm/history/:companySlug/*
  Returns git log for a specific file with diffs
  Params: ?limit=20

GET /api/fm/diff/:companySlug/*
  Params: ?from=[hash]&to=[hash]
  Returns unified diff between two commits for one file

POST /api/fm/branch/:companySlug
  Body: { branchName }
  Creates a new Git branch
  Branch naming convention: "draft/[slug]" or "release/v[n]"

POST /api/fm/release/:companySlug
  Body: { version, notes }
  Tags current HEAD: "release/v[version]"
  Generates RELEASE.md in /releases/ with:
    - All files signed in this release period
    - Clause counts by file type
    - Owner sign-off list
    - Compliance coverage matrix (which NIST controls are covered)
    - FM Agent auto-generated release summary (calls Anthropic API)
  Returns: { success, tag, releaseNotesPath }

GET /api/fm/status/:companySlug
  Returns governance health dashboard data:
  {
    totalFiles: n,
    byType: { AGENTS: n, SOP: n, SKILL: n, EXCEPTION: n, COMPLIANCE: n },
    byStatus: { draft: n, review: n, live: n, expired: n },
    expiringSoon: [ files expiring within 30 days ],
    unsigned: [ files with status != live ],
    lastCommit: { hash, message, date },
    totalCommits: n,
    coverageMatrix: { [nistControl]: { covered: bool, file: path } }
  }

POST /api/fm/agent/suggest/:companySlug/*
  Body: { fileContent, context }
  Calls Anthropic API to suggest improvements to a file
  Returns: { suggestions: [...], improvedContent: string }

POST /api/fm/agent/release-notes/:companySlug
  Body: { fromTag, toTag, fileList }
  Calls Anthropic API to write release notes
  Returns: { notes: string }

POST /api/fm/search/:companySlug
  Body: { query, filters: { type, axis, owner, status, domain } }
  Full-text search across all .md files
  Also matches on YAML front matter fields
  Returns: [ { file, excerpt, matchedClauses } ]

SUGGEST IMPROVEMENTS (/agent/suggest):

System prompt:
"""
You are the VDA-MD File Manager Agent. You review governance Markdown files 
and suggest precise, actionable improvements.

A great VDA-MD governance file:
1. Has complete YAML front matter (agent_id, domain, owner, axis, 
   journey_stage, status, baseline)
2. Uses only MUST / MUST NOT / MAY as rule prefixes — no passive voice, 
   no vague language
3. Has a specific, named escalation path (role names, not "the team")
4. Has a violation definition that is specific and testable
5. Has cross-domain inheritance rules if the agent touches finance, HR,

6. Has rules that are independently citable as single Witness Agent clauses

Review the provided file and output:
- A brief assessment (2-3 sentences)
- Up to 5 specific improvements with the exact text to add or change
- A rewritten version of any rule that is vague or passive voice
- Overall governance quality score: 0-100

Format as plain text (no JSON, no fences). Start with the score on line 1:
SCORE: [n]/100
Then your assessment and suggestions.
"""

AGENTS.md template (params: agentName, domain, owner, axis, stageId, company):
"""
---
agent_id: [slug of agentName]
domain: [domain]
owner: [owner]
axis: [axis]
journey_stage: [stageId]
normalisation_level: 3
vendor: VDA-MD Native
baseline: true
status: draft
company: [company]
created_at: [ISO date]
---

## Agent Scope
[agentName] is responsible for [axis === 'vertical' ? 'customer-facing' : 
'shared service'] operations in the [stageId] stage.

## Permitted Actions
- MUST [primary action] before proceeding
- MUST verify authorisation level matches required permissions
- MUST log every decision to the Witness Agent audit trail
- MUST NOT proceed with actions outside defined scope without escalation
- MAY [discretionary action] when conditions are met
- MAY escalate to [owner] when uncertain

## Escalation Path
- Routine exceptions → [owner]
- Cross-domain actions → Shared Services owner
- Policy violations → Compliance Director

## Cross-Domain Inheritance
Actions triggering financial transactions MUST inherit permissions from 
the Order-to-Cash Shared Services governance file.
Actions triggering HR data access MUST inherit permissions from the 
HR & Payroll Shared Services governance file.

## Violation Definition
Any action taken outside the Permitted Actions above, any cross-domain 
action without verified inheritance, or any decision not logged to the 
Witness Agent audit trail constitutes a violation.
"""

EXCEPTION.md template (params: exceptionTitle, owner, expiresAt, reason, stageId):
"""
---
agent_id: exception-[slug]
type: EXCEPTION
domain: [domain]
owner: [owner]
axis: [axis]
journey_stage: [stageId]
status: review
expires_at: [expiresAt]
exception_reason: [reason]
approved_by: [owner]
created_at: [ISO date]
---

## Exception Title
[exceptionTitle]

## Exception Scope
This exception temporarily overrides the standard baseline rules for 
[stageId] in the following specific scenario:

## Override Rules
- MAY [the exceptional action] until [expiresAt]
- MUST document every instance where this exception is invoked
- MUST NOT extend this exception without a new owner sign-off
- MUST revert to baseline rules on [expiresAt] automatically

## Expiry and Revert
This exception file expires on [expiresAt]. Upon expiry:
- The governing agent MUST revert to baseline AGENTS.md rules
- The Witness Agent will flag any continued exception invocations as violations
- A new EXCEPTION.md must be created and signed if extension is required

## Violation Definition
Invoking this exception outside the defined scope, after the expiry date, 
or without documenting the invocation constitutes a violation.
"""

CRITICAL IMPLEMENTATION NOTES
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. NEVER expose Git commands to the user. The entire Git layer is 
   invisible. Users see "Save", "Sign off", "Release" — not "commit", 
   "tag", "push".

2. NEVER hard-delete any file. Archive always. This is a governance 
   system — deletion of governance records is itself a compliance risk.

3. YAML front matter parsing: use the gray-matter library on the backend 
   to reliably parse and write front matter. On the frontend, parse it 
   manually for syntax highlighting (detect lines between --- markers).

4. The clause counter is critical for the governance health dashboard. 
   Count using these exact rules:
   - MUST clause: line starting with "- MUST " (must not contain "NOT")
   - MUST NOT clause: line starting with "- MUST NOT "
   - MAY clause: line starting with "- MAY "
   
5. The EXCEPTION.md expiry monitor must run on both frontend load 
   (check all files on mount) AND should set a daily interval check 
   (setInterval every 60 seconds in dev, daily in prod).

6. When the FM Agent writes its own commits (auto-commit on expiry 
   warning generation, release note creation), the Git author should 
   be "FM Agent <filemanager@vdamd.local>" to distinguish from 
   human author commits.

7. The editor must show a "dirty" state (isDirty = true) the moment 
   any character changes. The Save button should be disabled when 
   not dirty and bright orange when dirty. Navigating away from a 
   dirty file should show a confirmation dialog.

8. For the diff view — compute a simple line-diff on the client side 
   using a lightweight algorithm (you can use a simple LCS approach 
   or import diff from CDN: https://cdnjs.cloudflare.com/ajax/libs/
   jsdiff/5.1.0/diff.min.js). Keep it simple — added/removed/context 
   lines only, no word-level highlighting needed.

9. Marked.js for Markdown rendering (preview pane) — import from CDN:
   https://cdnjs.cloudflare.com/ajax/libs/marked/9.1.6/marked.min.js

10. The File Manager should initialise automatically on first use — 
    call POST /api/fm/init with the company slug and industry when 
    the tab first mounts if no files are found. This creates the 
    directory structure and bootstraps the Git repo.

11. For the "Request sign-off" feature in the FM Agent panel, generate 
    a copyable message like:
    "Hi [owner], your sign-off is required on [filename] in the 
    VDA-MD File Manager. This file governs [agentName] in the 
    [stage] stage. Please review and approve at [URL]. 
    Framework: VDA-MD · Company: [companyName]"
    Copy to clipboard via navigator.clipboard.writeText()

12. The governance coverage matrix in the FM Agent panel should map 
    config.nistControls to files in /compliance/ that contain that 
    control_id in their YAML front matter. A control is "covered" if 
    a live, signed compliance file exists for it.
