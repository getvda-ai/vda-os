#72 — Genesis-Driven EXCEPTION_AUTHORITY.md: AI-Derived Exception 
      Authority from Ingested Company Context

What & Why
EXCEPTION_AUTHORITY.md does not exist in VDA's generation pipeline. 
It is the single most important governance file for hotel operations — 
it defines what each role can approve autonomously, at what ceiling, 
and what always requires human sign-off. Without it, the CISO has 
nothing to review, the Hotel GM has nothing to confirm, and the crawl 
loop has no structure.

This file must be generated by VDA — not written by Rawson Consulting, 
not configured by the hotel — derived from the same context the genesis 
process already ingests: the company website, the industry, the brand 
context, the local jurisdiction, and any operational documents provided.

The generation uses the same AI pipeline that produces AGENTS.md and 
SOP.md, but asks different questions of the context: What does this 
hotel's rate policy imply about appropriate discount thresholds? What 
does their service recovery language imply about comp authority? What 
does the jurisdiction imply about mandatory HITL for certain decisions?

The CISO then reviews the AI-derived file during Stage 1 of the 
onboarding walkthrough — they are validating VDA's interpretation of 
the hotel's own policies, not configuring thresholds manually.

──────────────────────────────────────────────────────────────────────
The Generation Model
──────────────────────────────────────────────────────────────────────

Context sources (all already ingested or available in the DB):
  1. brandContext        — from companies table (website ingestion)
  2. industry            — "hospitality" 
  3. companyName         — e.g. "citizenM Hotels"
  4. existingFiles       — the agent's AGENTS.md + SOP.md content
     (the SOP contains the operating procedures the agent follows —
      this is the primary source for deriving exception ceilings)
  5. jurisdiction        — derived from Apaleo propertyId or companyId
     (BER=Germany, LND=UK, PAR=France, MUC=Germany, VIE=Austria)
  6. industryContext     — hospitality-specific regulatory knowledge:
     EU Rate Parity Regulations, GDPR Article 5, EU Consumer Rights 
     Directive, local consumer protection law per jurisdiction
  7. agentDomain        — e.g. "Revenue Management", "Checkout", 
     "Folio Management" (from existing agent AGENTS.md front matter)

The generator reads the agent's SOP.md and identifies every MAY clause 
— these are the conditional permissions, the "agent may do X under 
conditions Y". Each MAY clause maps to a potential exception class. The 
generator then:
  - Determines which role band has authority for that action
  - Derives a reasonable ceiling from the SOP context and industry norms
  - Determines whether that ceiling is autonomous or hitl_required based 
    on the risk level implied by the SOP language
  - Maps escalation targets from the RACI structure already in AGENTS.md

This is AI interpretation of the hotel's own documents. The ceiling 
numbers are not invented — they are derived from the SOP's language 
(e.g. "minor folio adjustments for billing errors" → €15 ceiling for 
Ambassador; "significant rate adjustments for corporate accounts" → 
Hotel GM hitl_required).

──────────────────────────────────────────────────────────────────────
The Jurisdiction Layer
──────────────────────────────────────────────────────────────────────

This is the layer that makes EXCEPTION_AUTHORITY.md different per hotel 
even within the same hotel group, without any manual configuration.

JURISDICTION_CONTEXT map (hardcoded in the generator, not in the DB):

  Germany (BER, MUC):
    - Preisangabenverordnung: displayed rates must match charged rates
      → Rate Agent MAY NOT apply undisclosed surcharges (MUST NOT clause)
      → Rate discount ceiling for Ambassador: max 10% (stricter than UK)
    - BDSG: stricter consent requirements for guest data processing
      → Check-In Agent ceiling: no automated profile enrichment without 
        explicit consent flag in Apaleo guest record

  United Kingdom (LND):
    - Consumer Rights Act 2015: service failures must be remedied
      → Service recovery comp ceiling: higher than EU baseline
      → Checkout Agent MAY comp up to £200 for documented service failure

  France (PAR):
    - Loi Evin restrictions on promotional language
      → Rate Agent: promotional language in rate descriptions must comply
    - RGPD (French GDPR implementation): stricter than base GDPR
      → Same as BDSG profile enrichment restriction

  Austria (VIE):
    - Konsumentenschutzgesetz: consumer protection provisions
      → Similar to German framework, apply German jurisdiction context

  Netherlands / EU baseline:
    - EU Consumer Rights Directive: withdrawal rights, transparency
    - EU AI Act Articles 13, 14, 17: applies to all EU jurisdictions
    - Apply as baseline for all EU properties

The generator reads the propertyId's jurisdiction and includes the 
relevant legal constraints as MUST NOT clauses and ceiling modifiers 
in the generated EXCEPTION_AUTHORITY.md.

Steps
──────────────────────────────────────────────────────────────────────

1. JURISDICTION_CONTEXT map
   New constant in fileManager.ts (or a dedicated jurisdictionContext.ts):
   Maps Apaleo property codes to jurisdiction objects:
     { BER: { country: "Germany", laws: [...], ceiling_modifiers: {...} }
       LND: { country: "UK", laws: [...], ceiling_modifiers: {...} }
       ... }
   Each jurisdiction object contains:
     - laws: array of { name, relevance, constraint_type }
     - ceiling_modifiers: per-agent-domain overrides
       e.g. { "Revenue Management": { ambassador_discount_max: 0.10 } }
     - mandatory_must_not_clauses: array of clauses derived from law
   Derive the property code from companyId using the COMPANIES constant 
   (companyId 1=BER, 2=LND, 3=MUC, 4=PAR, 5=VIE).

2. EXCEPTION_AUTHORITY.md generation prompt
   New function: generateExceptionAuthorityFile(params) in fileManager.ts
   Params: { agentId, companyId, agentsMd, sopMd, skillMd, 
             brandContext, companyName, industry, jurisdiction }
   
   The generation reads the SOP.md MAY clauses and maps each to an 
   exception_class. The AI prompt is:

   System: "You are a VDA-MD governance file generator. You generate 
   EXCEPTION_AUTHORITY.md files that define per-role-band exception 
   authority for AI agents. You derive exception classes and ceilings 
   FROM the agent's SOP.md content — you do not invent them. Every 
   exception class must trace to a MAY clause in the SOP.md."
   
   User: "Generate EXCEPTION_AUTHORITY.md for:
   Agent: [agentId]
   Company: [companyName]
   Domain: [domain from AGENTS.md front matter]
   Jurisdiction: [country], relevant laws: [laws array]
   
   SOP.md content (source for MAY clauses):
   [sopMd content]
   
   AGENTS.md content (source for RACI and escalation structure):
   [agentsMd content]
   
   Jurisdiction constraints that MUST appear as MUST NOT clauses:
   [mandatory_must_not_clauses from JURISDICTION_CONTEXT]
   
   Ceiling modifiers for this jurisdiction:
   [ceiling_modifiers from JURISDICTION_CONTEXT]
   
   Generate the complete EXCEPTION_AUTHORITY.md following the schema:
   - YAML front matter with file_type, agent_id, jurisdiction, 
     crawl_agreement_threshold, sandbox_pass_threshold
   - One role_band section per band (ambassador through compliance_officer)
   - Each exception_class with: description, ceiling, ceiling_type, 
     authority (autonomous | hitl_required | not_applicable),
     escalate_to, must_log: true
   - escalation_targets map derived from AGENTS.md RACI section
   - must_not_override section derived from MUST NOT clauses in SOP.md
   - jurisdiction_notes section citing applicable laws
   
   Every exception class ceiling MUST trace to a specific MAY clause 
   in the SOP.md. Include the source clause reference."

3. POST /api/fm/generate-exception-authority endpoint
   Body: { agentId, companyId, regenerate?: boolean }
   
   On request:
     - Fetch agent's AGENTS.md, SOP.md, SKILL.md from governance_files 
       WHERE agentId=X AND companyId IN (companyId, 0) 
       (hotel-specific first, fallback to companyId=0)
     - Fetch brandContext from companies table
     - Derive jurisdiction from COMPANIES constant + JURISDICTION_CONTEXT
     - Call generateExceptionAuthorityFile()
     - Run compliance check on generated content
     - If regenerate=false and existing EXCEPTION_AUTHORITY exists: 
       return existing without regenerating
     - If regenerate=true or no existing file: save to governance_files
       and return new file
   
   Returns: { file, complianceCheck, jurisdictionApplied, sourceClauses }
   sourceClauses: array of { exceptionClass, tracedToClause } so CISO 
   can verify derivation

   SKILL.md, call generateExceptionAuthorityFile() with the same 
   context. Add the result as a fourth file: exceptionAuthorityFile.
   Update the generate_candidate_governance_files tool definition to 
   include exception_authority_md as a fourth parameter.
   
   The A2A pipeline (onboardingOrchestrator.ts Phase 3) already saves

   EXCEPTION_AUTHORITY.md.

5. fm/agent/suggest accepts EXCEPTION_AUTHORITY fileType
   Extend the fileType handling in POST /api/fm/agent/suggest to accept 
   "EXCEPTION_AUTHORITY". When fileType=EXCEPTION_AUTHORITY: use the 
   jurisdiction-aware prompt from Step 2 rather than the generic 
   governance file prompt.

6. §4 compliance guard for EXCEPTION_AUTHORITY
   In the PUT /api/fm/file/:id handler (file update path):
   When fileType === "EXCEPTION_AUTHORITY":
     - Parse the new and saved content
     - For each exception_class: if new ceiling < saved ceiling → allowed 
       (more restrictive is always permitted)
     - If new ceiling > saved ceiling → dilution, require CO override modal
     - If authority changes from hitl_required → autonomous → dilution
     - If any entry in must_not_override is removed → critical dilution
   Add these checks to the existing dilution detection logic.
