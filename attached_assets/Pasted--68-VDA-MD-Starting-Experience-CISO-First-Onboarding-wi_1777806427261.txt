#68 — VDA-MD Starting Experience: CISO-First Onboarding with 
      Stage-by-Stage Walkthrough

What & Why
The current platform drops a first-time CISO into a Command Centre that 
shows hotels and agents with no explanation of what has been validated, 
what needs to happen before anything can run, or what order to do it in.

The real problem: compliance is not provable from the current UI. A CISO 
needs to see — stage by stage — what each agent does, what it can and 
cannot do, what it outputs in Apaleo, what the Witness Agent records, and 
then sign it off. Only after that sign-off does the Hotel GM see anything.

This task replaces the starting screen with a three-track onboarding 
console that enforces the correct sequence:

  Track 1  CISO: VDA Native Agent Admission
           One agent at a time. Stage-by-stage walkthrough. Fully 
           observable. Restartable. CISO signs off each agent before 
           Hotel GM can touch it.

  Track 2  Hotel: Crawl → Walk → Run  
           One agent at a time. One hotel at a time for crawl. 
           Exception confirmation from EXCEPTION_AUTHORITY.md before 
           crawl starts. HITL loop by role during crawl. Baseline 
           checkbox converts observed exceptions into standing permissions.

  Track 3  A2A External Agent Admission
           Same CISO-first admission flow as Track 1, then Hotel CWR.

The starting screen IS the governance proof. When a CISO has completed 
Track 1 for an agent, every step they took is in the Witness Agent trail.
That trail is the EU AI Act Article 17 documentation.

──────────────────────────────────────────────────────────────────────
TRACK 1: CISO VDA NATIVE AGENT ADMISSION WALKTHROUGH
──────────────────────────────────────────────────────────────────────

Clicking "Start →" on Track 1 opens the CISO Walkthrough for the first 
unadmitted agent. This is a full-screen stage-by-stage flow.

AGENT SELECTOR
  Top bar shows all 8 VDA native agents as tabs:
    Availability Agent  Rate Agent  Reservation Bot  Check-In Agent
    Folio Agent  Folio Charge Agent  Checkout Agent  Revenue Reconciliation
  Each tab shows status badge: ⏳ Pending  ✅ Admitted  ❌ Rejected
  CISO can jump to any agent. Progress is saved per agent.
  
  First time: Rate Agent is pre-selected (the reference implementation).

STAGE STRUCTURE
  Each agent has 6 stages. A persistent left sidebar shows all stages 
  with completion status. Each stage has:
    - Stage content (read-only display of evidence)
    - A confirmation checkbox: "I have reviewed this stage"
    - A [Next →] button (disabled until checkbox is checked)
    - A [Restart this agent] button (always visible, resets all stages 
      for this agent, clears any partial admission state)
  Progress is persisted in localStorage keyed by agentId so browser 
  refresh does not lose position.

  Calls: POST /api/onboarding/:id/run-sandbox

  Scenario 2: 8% rate discount request — expected PASS (within ceiling)
  Scenario 3: 22% rate discount request — expected ESCALATE (above ceiling)
  Scenario 4: Rate request with MUST NOT condition — expected FAIL
  Scenario 5: Cross-property rate with no authority — expected ESCALATE

  Each scenario shows:
    Input: what was asked
    Governance files consulted: [AGENTS.md ✓] [SOP.md ✓] [SKILL.md ✓]
    Decision: PASS / FAIL / ESCALATE (with colour)
    Governance clause that applied (quoted from the file)
    Witness entry ID written: #NNN

Pass rate shown at bottom: X/5 passed correctly.
If pass rate < threshold from onboarding-policy.md: red warning, 
  Next button disabled. "Re-run to try again."

Confirmation checkbox: "I have reviewed all 5 scenarios and the agent's 
  decisions are correct."

─────────────────────────────
STAGE 6: ADMIT OR REJECT
─────────────────────────────
Title: "Final decision"

Summary panel — shows completion of Stages 1–5:
  ✅ Stage 1: Governance files reviewed
  ✅ Stage 2: Sandbox pass rate: 5/5
  ✅ Stage 3: Apaleo CRUD scope confirmed
  ✅ Stage 4: Witness audit trail verified
  ✅ Stage 5: Exception authority ceilings confirmed

Declaration text (non-editable):
  "I, [CO name / role], confirm that Rate Agent has been reviewed in full 
   against VDA-MD governance standards. The agent's governance files, 
   operational scope, audit trail, and exception authority are acceptable 
   for deployment at citizenM properties. This admission is recorded in 
   the Witness Agent trail."

Two actions:

  [✅ Admit to Framework]  (green)
    Calls: POST /api/onboarding/:id/admit
    On success: 
      - Stage 6 shows green "Admitted" confirmation
      - Witness entry written: event_type="agent_admitted"
      - Agent tab in top bar updates to ✅
      - Toast: "Rate Agent admitted. Hotel GM can now enable crawl."
    Returns to agent selector. Next unadmitted agent is pre-selected.

  [❌ Reject] (red, opens modal)
    Modal title: "Reject Rate Agent"
    Mandatory reason field (textarea, min 20 chars)
    [Confirm Rejection] button
    Calls: POST /api/onboarding/:id/reject { reason }
    On success:
      - Witness entry written: event_type="agent_rejected", reason logged
      - Agent tab updates to ❌
      - Toast: "Rate Agent rejected. Amend governance files and restart."

Steps
──────────────────────────────────────────────────────────────────────

1. New starting screen component: OnboardingConsole
   Replace the current Directory root with OnboardingConsole when no 
   agents have phase="run" and no setup has been selected.
   Once any setup is selected (hotel hub navigation), the existing 
   Command Centre still works as before — OnboardingConsole is the 
   zero-state and "return to start" screen only.
   Three-column layout (equal width). Data sources:
     Track 1: GET /api/onboarding?source=vda_native
     Track 2: GET /api/dashboard/phases/portfolio
     Track 3: GET /api/onboarding?source=a2a_external
   Track 2 locked state: when Track 1 admitted count = 0.

2. CISO Walkthrough component: CISOWalkthrough
   New component in VdaOS.jsx. Full-screen modal overlay.
   Props: agentId, onboardingRequestId, source ("vda_native" | "a2a_external")
   State: currentStage (1–6), stageCompletions (bool[6]), 
     sandboxResults, localStorage sync
   Left sidebar: stage list with completion indicators
   Main content: stage-specific render (see steps 3–8)
   Top bar: agent selector tabs with status badges
   Persistent [Restart this agent] button in top-right

3. Stage 1 renderer: GovernanceFileReview
   Fetch GET /api/governance-files?agentId=X&companyId=0 for all 4 files.
   Tab switcher: AGENTS.md | SOP.md | SKILL.md | EXCEPTION_AUTHORITY.md
   Right panel: parse and count MUST/MUST NOT/MAY clauses using existing 
     compliance guard logic. Show NIST refs. Build ceiling table from 
     EXCEPTION_AUTHORITY.md role_band sections.
   Missing file: red alert, Next disabled, suggests running seed script.

4. Stage 2 renderer: SandboxEvaluation
   [Run Sandbox Evaluation] calls POST /api/onboarding/:id/run-sandbox
   New backend endpoint in onboardingRollback.ts (or admin.ts):
     Runs 5 predefined scenarios against the agent's route in agents.ts
     Each scenario: POST /api/a2a/1/{agentSlug} with test payload
     Records Witness entry per scenario
     Returns: array of { scenario, input, decision, clause, witnessId, passed }
   Frontend polls for result or uses response directly.
   Renders per-scenario result rows with colour-coded decision badges.
   Pass rate check against onboarding-policy.sandbox_pass_threshold.

5. Stage 3 renderer: ApleoCRUDReview
   Parse SKILL.md for API endpoint references (regex: Apaleo API paths)
   Parse AGENTS.md MUST clauses for write operations
   Show two-column READ/WRITE table
   [Test Apaleo Connection] calls GET /api/apaleo/health?companyId=1
   Shows response status and latency.

6. Stage 4 renderer: WitnessReview
   Fetch last 5 Witness entries for this agentId from Stage 2 sandbox run
   (filter by session or timestamp since Run Sandbox was clicked)
   Render formatted entry cards with all fields visible
   EU AI Act compliance mapping: hardcoded to Article 13/14/17 for now
   [Download SOC 2 excerpt] generates a text blob with the entries

7. Stage 5 renderer: ExceptionAuthorityConfirmation
   Parse EXCEPTION_AUTHORITY.md role_band sections
   Render one confirmation card per exception_class per front-line band
   Individual checkbox per class (min 1 AGENTS.md MUST ceiling per card)
   All individual checkboxes must be checked for stage confirm to enable
   Display hitl_required classes with distinct styling and note that 
     they ALWAYS generate cards even in walk/run

8. Stage 6 renderer: AdmitOrReject
   Summary checklist of completed stages
   Declaration text with role and timestamp
   [Admit] → POST /api/onboarding/:id/admit
     On success: update localStorage, update agent tab badge, return to 
     agent selector showing next unadmitted agent
     Write stage completion Witness entry: "ciso_walkthrough_completed"
   [Reject] → modal with mandatory reason textarea (min 20 chars)
     POST /api/onboarding/:id/reject
     On success: agent tab badge → ❌

9. Stage completion Witness entries
   On each Next → click: POST /api/witness (or inline in agent endpoint):
     event_type: "ciso_stage_completed"
     stage: N  (1-5)
     agentId, companyId: 0
     decidedBy: currentRole
   This means the Witness trail documents every stage the CISO reviewed,
   not just the final admit decision.

10. Pre-crawl exception confirmation component: PreCrawlConfirmation
    Shown in Track 2 when agent is admitted but not yet in crawl at hotel.
    Parse EXCEPTION_AUTHORITY.md front-line bands.
    One accordion section per band (ambassador, senior_ambassador, hotel_gm).
    Each exception_class shown with: description, ceiling, ceiling_type, 
      authority, escalate_to.
    hitl_required classes: labelled "Always requires approval — never autonomous"
    One checkbox per BAND (not per class — band-level confirmation):
      "☐ I understand [band] staff will receive decision cards for these 
       exception classes during crawl"
    All three band checkboxes must be checked for Enable Crawl to appear.
    State persisted in localStorage per agentId+companyId.

11. Crawl progress dashboard component: CrawlProgressDashboard
    Polls GET /api/dashboard/activation/:agentId/crawl-status?companyId=X 
    every 30 seconds.
    Per-band progress bars (resolved/total).
    Recent decisions feed: poll GET /api/witness-entries?agentId=X&companyId=Y
      &limit=10&since=[crawl start timestamp]
    When crawlComplete=true: green banner + Promote to Walk button.

12. Baseline checkbox on DecisionCard.jsx
    As specified in Task #67 Step 13 (unchanged from that spec):
    Show only when payload.current_phase === "crawl"
    Checkbox label: "☐ Authorise agent to handle [payload.exception_class] 
      autonomously at this hotel going forward — will not appear again"
    Submit label changes on check.
    POST includes authoriseAsBaseline.
    Toast on baselined=true.

13. localStorage persistence layer
    Key pattern: vda_ciso_{agentId}_stage   → int (1-6)
    Key pattern: vda_ciso_{agentId}_stages  → bool[6] JSON
    Key pattern: vda_crawl_{agentId}_{companyId}_confirmed → bool[3] JSON
    [Restart this agent] clears all keys for that agentId:
      Deletes localStorage keys
      Calls POST /api/onboarding/:id/restart (new endpoint) which sets 
        status back to "pre_admitted", clears any sandbox results stored
        on the record
      Does NOT delete Witness entries

14. POST /api/onboarding/:id/restart endpoint
    Sets onboarding_requests.status = "pre_admitted"
    Clears evalPassRate, firstHitlToken fields on the record
    Writes Witness entry: event_type="ciso_walkthrough_restarted",
      agentId, restartedBy, timestamp
    Returns updated record

15. Verification sequence
    a. Load platform fresh. Confirm OnboardingConsole renders with 3 tracks.
       Track 2 shows "Locked — admit an agent first".
    b. Click Track 1 Start. Confirm CISOWalkthrough opens for Rate Agent.
    c. Stage 1: all 4 files render. Compliance summary shows clause counts.
       Checkbox disabled until all files loaded. Check box. Next → enabled.
    d. Stage 2: click Run Sandbox. All 5 scenarios run. Pass rate = 5/5.
       Witness entries created (check Witness Agent tab shows new entries).
       Check box. Next →.
    e. Stage 3: READ/WRITE table renders. Test Apaleo connection returns 200.
       Check box. Next →.
    f. Stage 4: last 5 Witness entries from Stage 2 visible. EU AI Act 
       mapping shows. Check box. Next →.
    g. Stage 5: all exception class cards render by band. Check all individual
       cards. Stage confirm checkbox enabled. Check box. Next →.
    h. Stage 6: all 5 stages show ✅. Click Admit.
       Confirm status = "admitted" in DB.
