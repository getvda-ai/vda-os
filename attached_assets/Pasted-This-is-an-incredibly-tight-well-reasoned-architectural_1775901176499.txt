This is an incredibly tight, well-reasoned architectural spec. You have successfully translated the high-level concept of Cryptographic Agent Identity into a concrete, executable plan.

The absolute most brilliant part of your design is binding the governance_file_hash into the credential. This transforms the VC from a simple "auth token" into a deterministic lock. If a domain owner updates an EXCEPTION.md file, the hash changes, the agent's current credential instantly mismatches the DB reality, and the API drops the request with a 401 before the LLM can even think about executing an outdated rule. That is enterprise-grade security.

Your architecture, constraints, and task list are correct and ready to build, but because you are using the @digitalbazaar ecosystem, there are a few highly specific "gotchas" you need to account for in your implementation to prevent hours of debugging.

Here is the candid technical feedback on the edge cases:

1. The @digitalbazaar Signature Suite Requirement
The @digitalbazaar/vc package handles the mechanics of issuing and verifying, but it does not contain the cryptographic suites themselves.

The Fix: You must also install a signature suite package. Since you are using did:key and Ed25519, you will need to add @digitalbazaar/ed25519-signature-2020 (or eddsa-2022). You will pass this suite into the vc.issue({ suite }) and vc.verify({ suite }) functions.

2. The JSON-LD Document Loader Trap (Crucial)
W3C Verifiable Credentials inherently use JSON-LD (Linked Data). When you call vc.issue() or vc.verify(), the library will look at the @context array (e.g., ["https://www.w3.org/2018/credentials/v1"]) and attempt to fetch those URLs over the internet to validate the schema.

The Problem: If W3C servers are rate-limiting (which they frequently do), or if your server has a network hiccup, your middleware will hang or crash, taking down your agents.

The Fix: You must implement a custom "Document Loader" in your verifyAgentCredential.ts and agentCredentialIssuer.ts files. This is a function that catches requests to standard W3C URLs and returns a locally cached JSON object instead of hitting the network.

3. Placing Custom Claims correctly
When you generate the VC, make sure your custom fields (permitted_skills, governance_file_hash, domain_owner) are placed inside the credentialSubject object, not at the root of the VC.

Correct Structure:

JSON
{
  "@context": [...],
  "type": ["VerifiableCredential", "AgentGovernanceCredential"],
  "issuer": "did:key:z6Mk...",
  "issuanceDate": "2026-04-11T10:00:00Z",
  "expirationDate": "2026-04-12T10:00:00Z",
  "credentialSubject": {
    "id": "did:key:z6MkAgent...", 
    "companyId": "citizenM-AMS",
    "agentId": "CheckoutAgent",
    "governance_file_hash": "a1b2c3d4..."
  }
}
4. Future-Proofing node-cron
Using node-cron to rotate credentials every 23 hours is perfectly fine for this standalone API server phase.

The Future Warning: node-cron runs in the memory of the Node.js process. When you eventually scale this API server to multiple instances (e.g., behind a load balancer), every instance will trigger the cron job simultaneously. For now, it's exactly what you need. Later, you'll want to either rely on a DB-locked job queue (like BullMQ) or a Kubernetes CronJob.
