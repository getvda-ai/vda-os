What Replit got right
The task ordering is correct and the dependency chain is sound. DB schema and seed first, then API routes, then shared components, then role views, then the hub restructure. Building the views before the API routes would mean building against mocked data — the sequence prevents that.
The differentiated seed data across all 5 hotels is a smart addition beyond what the prompt specified. VIE as the reference, BER most advanced, LND mid-progression, MUC just starting, PAR blank-slate gives every role view something meaningful to display on first load. The Operations Chief chain view in particular needs real variation across properties to be demonstrable — a uniform seed would make it look like a single property repeated five times.
The useDashboard.js shared polling hook is the right abstraction. Five role views all need polling with cleanup — putting that logic in one place rather than duplicating setInterval/clearInterval patterns across five components prevents the memory leak problem the prompt called out.
Scoping out authentication explicitly is correct. The role switcher as UI-only session state is the right call for now — adding auth would block the build on infrastructure that isn't needed for the Apaleo demo.
Two things to watch in implementation
The SeniorAmbassadorView polls HITL pending every 10 seconds and shift summary every 30 seconds simultaneously. That's two independent polling intervals in one component. The useDashboard hook needs to handle multiple polling intervals with independent cleanup — confirm this is in scope for Task 3 before Task 4 starts, or the Senior Ambassador view will be the one that leaks.
The "next agent to activate" business case callout in the Hotel GM staircase — the one that says "In the last 30 days there were N decisions this agent could have handled" — requires a query against witness_entries filtered by agent type and date range. This isn't covered in the /api/dashboard/phases endpoint and isn't explicitly added to /api/dashboard/shift-summary. It should be a field on the /api/dashboard/phases response: add a potential_autonomous_decisions computed field per agent that returns the 30-day count from witness_entries where agent_id matches and decision = 'PASS'. Otherwise the Hotel GM staircase will have to make a separate query per agent row, which is 9 sequential calls.
The one genuine gap
The shadow review endpoint POST /api/dashboard/shadow-review writes a COMPLIANCE_BOUNDARY/INFO witness entry as specified. But the GET /api/dashboard/shift-summary response includes shadow_reviews — those are the unreviewed crawl-phase decisions the Ambassador needs to see. The spec doesn't define how the shift-summary endpoint knows which shadow decisions have already been reviewed. It needs a filter: return only witness entries where event_type = 'shadow_decision' AND no corresponding shadow_review_response entry exists for the same reviewed_decision_witness_id. Add this filter logic to Task 2 before Task 4 builds against it, otherwise reviewed decisions will keep reappearing.
Verdict
Implement as written with two additions before Task 4 starts: add potential_autonomous_decisions to the phases API response, and add the reviewed-filter logic to the shift-summary query. Both are Task 2 additions — no structural changes needed. Green light.
