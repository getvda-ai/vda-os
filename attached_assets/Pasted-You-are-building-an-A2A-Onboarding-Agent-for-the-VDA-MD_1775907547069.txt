You are building an A2A Onboarding Agent for the VDA-MD Framework running on 
Replit. This agent governs the process of adding external agents to the VDA-MD 
framework. It uses the framework to govern itself — the same AGENTS.md, SOP.md, 
SKILL.md, EXCEPTION.md files, the same Witness Agent audit trail, the same HITL 
approval gates, and the same Git change management as every other governed 
workflow in the system.

The following are already built and live:
- Add-on 1: W3C Verifiable Credentials middleware (verifyAgentCredential.ts)
- Add-on 2: Red Team Eval Pipeline (evalWebhook, evalRunner, DeepEval scoring)
- Add-on 3: HITL Decision Cards (hitlEscalation, hitlCardGenerator, Resend email)
- Add-on 4: Structured Output Enforcement (Ajv schema registry, tool_use forcing)
- A2A Protocol: JSON-RPC 2.0 handler, Agent Card registry, a2a_tasks table
- Witness Agent: witness_entries table with event_category field

This agent is the 9th agent in the VDA-MD system. It joins the existing 8:
availability-agent, rate-agent, reservation-bot, check-in-agent, folio-agent,
folio-charge-agent, checkout-agent, revenue-reconciliation-agent.

   ## Onboarding Agent
   Governs the addition of external agents to the VDA-MD framework.
   Operates at platform scope across all company instances.

   ### Agent Rules
   - MUST verify VC before accepting any onboarding request
   - MUST run full impact delta analysis before generating candidate files
   - MUST auto-remove duplicate skills from candidate SKILL.md before HITL
   - MUST NOT approve agents that claim skills outside their declared domain
   - MUST NOT commit governance files without two HITL approvals
   - MUST NOT approve its own onboarding requests
   - MUST NOT make direct push to main branch under any circumstance
   - MUST run sandbox eval (Add-on 2) before second HITL gate
   - MUST create rollback reference before any production commit
   - MUST surface RACI conflicts as named exceptions, not blockers
   - MAY auto-generate candidate governance files from Agent Card content
   - MAY auto-remove duplicate skills with Witness log entry

   domain: Governance
   owner: Compliance Officer
   nist_control: SA-4
   mustCount: 9
   mustNotCount: 5
   mayCount: 2
   ---
   ## Onboarding Agent SOP

   ### Phase 1 — Discovery and Validation
   - MUST verify the external agent presents a valid W3C VC Bearer token
   - MUST extract Agent Card from the A2A tasks/send payload
   - MUST validate Agent Card conforms to A2A spec fields:
     name, description, url, version, capabilities, skills, authentication
   - MUST NOT proceed if Agent Card is malformed or VC is invalid

   ### Phase 2 — Impact Delta Analysis
   - MUST analyse all 8 existing agent SKILL.md files for skill overlap
   - MUST query witness_entries for ESCALATE events in last 30 days
     matching any skill the new agent declares
   - MUST check all SOP.md MAY clauses for currently unexercised permissions
     the new agent could activate
   - MUST check all cross-domain inheritance gaps the new agent could close
   - MUST identify MUST NOT boundary overlaps with existing agents
   - MUST identify authority threshold collisions in Shared Services Finance
   - MUST auto-remove duplicate skills from candidate SKILL.md
   - MUST NOT block onboarding for RACI ambiguity — surface as exception

   ### Phase 3 — Candidate File Generation
   - MUST generate: candidate AGENTS.md, SOP.md, SKILL.md for new agent
   - MUST generate: EXCEPTION.md if any requested capability deviates from baseline
   - MUST generate: list of all existing files requiring modification
   - MUST validate all candidate files pass Compliance Guard before HITL

   ### Phase 4 — First HITL Gate
   - MUST send Decision Card to domain owner + Compliance Officer
   - Decision Card MUST include full Impact Delta Report
   - MUST NOT proceed to sandbox without both approvals
   - Reject → terminate with Witness entry, no files written

   ### Phase 5 — Sandbox Evaluation
   - MUST trigger Add-on 2 eval pipeline against candidate governance files
   - MUST require pass rate >= 0.95 before second HITL
   - MUST attach eval report to second HITL card

   ### Phase 6 — Second HITL Gate and Production
   - MUST send second Decision Card with eval results attached
   - MUST NOT commit to main without this second approval
   - On approval: commit via PR only, issue VC, register Agent Card
   - MUST write Witness entry: agent_onboarded with PR reference

   SKILL.md content to store:
   ---
   control_id: governance-onboarding-skill
   domain: Governance
   owner: Compliance Officer
   ---
   ## Permitted Skills
   - read_all_governance_files: READ all AGENTS.md, SOP.md, SKILL.md,
     EXCEPTION.md files across all agents and companies
   - read_witness_log: QUERY witness_entries for impact delta analysis
   - write_candidate_files: WRITE to staging branch only, never main
   - call_eval_pipeline: TRIGGER Add-on 2 eval against candidate files
   - trigger_hitl: CALL POST /hitl/escalate for both approval gates
   - commit_via_pr: CREATE pull request to governance repo, never direct push
   - issue_vc: CALL POST /api/agents/credentials/issue for approved agent
   - register_agent_card: ADD new agent to A2A Agent Card registry

   ## NOT Permitted
   - direct_push_to_main: under any circumstance
   - modify_must_not_clauses: in any existing governance file
   - self_approval: cannot approve its own onboarding or any request
     where it is the subject

2. IMPACT DELTA ANALYSER (server/onboarding/impactDeltaAnalyser.ts)

   This is the core intelligence of the Onboarding Agent. It receives the
   new agent's Agent Card and produces a structured ImpactDeltaReport before
   any candidate files are generated.

   Input: { agentCard: A2AAgentCard, companyId: number }

   Process:

   a. SKILL OVERLAP DETECTION
      - Load all existing SKILL.md files from DB for all 8 agents
      - Parse permitted skills from each file
      - Compare against skills array in the incoming Agent Card
      - For each overlap: record { skill, existingAgent, existingFile,
        conflictType: "duplication" | "must_not_boundary" | "authority_collision" }
      - Skills that are exact duplicates: flag for auto-removal from candidate
      - Skills that overlap a MUST NOT clause: flag as governance_conflict
        (requires HITL exception, not auto-removal)
      - Skills that overlap financial authority thresholds in Shared Services
        Finance SOP.md: flag as authority_collision

   b. FRICTION REDUCTION DETECTION
      - Query witness_entries WHERE decision = 'ESCALATE' AND created_at >
        NOW() - INTERVAL '30 days'
      - For each ESCALATE event: check if any skill in the new Agent Card
        matches the clause_applied that caused the escalation
      - If match: record { escalation_count, clause, agent_id, skill_match }
        as friction_removed entry
      - Count total weekly ESCALATE events that could be auto-resolved

   c. VALUE ADDITION DETECTION
      - Query all SOP.md files for MAY clauses
      - Identify MAY clauses that have never appeared in a witness_entry
        as clause_applied (unexercised permissions)
      - For each unexercised MAY: check if new agent's skills could activate it
      - Record as { may_clause, governance_file, activating_skill }
      - Query cross-domain inheritance check failures in witness_entries
        (event_type: "cross_domain_inheritance_failed" if logged, else infer
        from ESCALATE events with cross_domain flag)
      - Identify gaps the new agent could close

   d. JOURNEY STAGE MAPPING
      - Determine which journey stage(s) the new agent operates in based on
        its declared skills and domain in the Agent Card
      - Check the Two-Axis Governance Map: does a clear domain owner exist
        for this intersection in the YAML front matter of existing files?
      - If clear owner exists: assign as primary HITL approver
      - If ambiguous (cross-domain intersection with no single owner):
        identify both candidate owners and flag as raci_exception

   e. AFFECTED FILES LIST
      - Determine which existing governance files need cross-reference updates
        if the new agent is approved:
        * AGENTS.md files that inherit from the new agent's domain
        * SOP.md files with MAY clauses the new agent activates
        * Journey stage files where the new agent participates
      - This list becomes the PR scope — no files outside this list
        are touched during onboarding

   Output: ImpactDeltaReport {
     friction_removed: [{
       escalation_count: number,
       escalations_per_week: number,
       clause: string,
       affected_agent: string,
       resolving_skill: string
     }],
     value_added: [{
       type: "may_clause_activated" | "cross_domain_gap_closed",
       description: string,
       governance_file: string,
       activating_skill: string
     }],
     conflicts: [{
       type: "duplication" | "must_not_boundary" | "authority_collision",
       skill: string,
       existing_agent: string,
       existing_file: string,
       resolution: "auto_removed" | "hitl_exception" | "blocks_onboarding"
     }],
     raci_exceptions: [{
       intersection: string,
       candidate_owners: string[],
       resolution: "both_notified"
     }],
     auto_removed_skills: string[],
     affected_files: string[],
     files_to_create: number,
     files_to_modify: number,
     rollback_scope: string
   }

3. CANDIDATE FILE GENERATOR (server/onboarding/candidateFileGenerator.ts)

   Input: { agentCard: A2AAgentCard, impactDelta: ImpactDeltaReport }

   Calls Claude API (claude-sonnet-4-20250514) using tool_use forcing
   (Add-on 4 pattern) with a tool called "generate_candidate_governance_files"
   whose input_schema requires:
   {
     agents_md: string,
     sop_md: string,
     skill_md: string,
     exception_md: string | null,
     files_to_modify: [{
       filename: string,
       modification_description: string,
       new_content: string
     }]
   }

   System prompt instructs Claude to:
   - Generate AGENTS.md with YAML front matter derived from Agent Card fields
     (name → control_id, domain derived from journey stage mapping,
     owner from RACI resolution, skills from Agent Card minus auto_removed_skills)
   - Generate SOP.md with MUST/MUST NOT/MAY clauses appropriate to the
     declared domain — MUST count >= 3, MUST NOT count >= 1 mandatory minimum
   - Generate SKILL.md listing only skills not in auto_removed_skills,
     each with explicit permitted conditions and NOT permitted section
   - Generate EXCEPTION.md only if any skill deviates from baseline — null otherwise
   - Generate modification content for each file in affected_files list
     (add cross-references, update inheritance declarations)
   - All YAML front matter must include: owner, nist_control (closest match),
     approved_by: "PENDING", expires (1 year from today), risk_level

   After generation: validate all candidate files through Compliance Guard
   logic (check MUST counts, NIST references, ISO 42001 citations) before
   proceeding. If any file fails: return error, do not proceed to HITL.

4. ONBOARDING ORCHESTRATOR (server/onboarding/onboardingOrchestrator.ts)

   This is the main workflow controller. It is called by the A2A handler
   when a tasks/send request arrives at the onboarding-agent endpoint.

   The orchestrator manages state via a new DB table: onboarding_requests

   Add to lib/db/src/schema/:
   onboarding_requests table:
   - id (uuid PK)
   - session_id (varchar — from A2A task)
   - external_agent_did (varchar)
   - agent_card (jsonb — the submitted Agent Card)
   - impact_delta_report (jsonb)
   - candidate_files (jsonb)
   - eval_report_job_id (varchar nullable)
   - eval_pass_rate (numeric nullable)
   - first_hitl_token (varchar nullable)
   - first_hitl_outcome (varchar nullable — approved/rejected)
   - first_hitl_decided_at (timestamptz nullable)
   - second_hitl_token (varchar nullable)
   - second_hitl_outcome (varchar nullable)
   - second_hitl_decided_at (timestamptz nullable)
   - pr_number (varchar nullable)
   - pr_url (varchar nullable)
   - status (varchar: received|analysing|awaiting_first_hitl|sandbox|
             awaiting_second_hitl|committing|onboarded|rejected|failed)
   - created_at (timestamptz)
   - updated_at (timestamptz)

   Workflow steps (each updates status field before proceeding):

   STEP 1 — received
   Validate VC, validate Agent Card structure, write Witness entry:
   { event_type: "a2a_onboarding_request_received", external_agent_did,
     agent_card_name, session_id }

   STEP 2 — analysing
   Call impactDeltaAnalyser. Store ImpactDeltaReport in DB.
   Write Witness entry: { event_type: "impact_delta_complete",
     friction_removed_count, value_added_count, conflicts_count,
     auto_removed_skills, raci_exceptions_count }

   STEP 3 — candidate file generation
   Call candidateFileGenerator. Store candidate files in DB.
   Run Compliance Guard validation on all candidate files.
   Write Witness entry: { event_type: "candidate_files_generated",
     files_created_count, files_modified_count, compliance_guard_passed }

   STEP 4 — awaiting_first_hitl
   Build first HITL Decision Card payload. The card content must include:
   - summary: plain English description of what agent wants to join
   - impact_delta_report: full structured report from Step 2
   - candidate_files_summary: list of files to be created/modified
   - conflicts: all conflicts with resolution status
   - auto_removed_skills: list with explanation
   - raci_exceptions: list with both owners notified
   - risk_level: derived from highest conflict type found
   - recommended_action: "Approve" if no governance_conflict or
     blocks_onboarding conflicts, else "Reject"
   Call POST /hitl/escalate with this payload.
   For RACI exceptions: send additional notification to both candidate
   owners (second Resend email, not a HITL gate — informational only).
   Store first_hitl_token. Write Witness entry:
   { event_type: "first_hitl_issued", hitl_token, approver }

   STEP 5 — sandbox (triggered when first_hitl_outcome = "approved")
   Call the Add-on 2 eval pipeline by writing an eval job to /eval-queue/
   with the candidate SOP.md content as the changed_file context.
   Poll job status every 60 seconds.
   Store eval_report_job_id and eval_pass_rate when complete.
   Write Witness entry: { event_type: "sandbox_eval_complete",
     job_id, pass_rate, overall_result }
   If pass_rate < 0.95: set status = "failed", write Witness ESCALATE entry,
   notify first HITL approver via Resend that eval failed.
   Do NOT proceed to second HITL if eval failed.

   STEP 6 — awaiting_second_hitl
   Build second HITL Decision Card. This card must include everything
   from first card PLUS:
   - eval_pass_rate displayed as percentage
   - eval_scenario_summary: how many passed, how many failed, which
     clauses were tested, which clause (if any) caused failures
   - eval_report_job_id for reference
   - statement: "Agent passed {n}/20 governance scenarios in sandbox.
     Approving this card commits governance files to production and
     issues a cryptographic credential to the new agent."
   Call POST /hitl/escalate with second card payload.
   Store second_hitl_token. Write Witness entry:
   { event_type: "second_hitl_issued", hitl_token, eval_pass_rate }

   STEP 7 — committing (triggered when second_hitl_outcome = "approved")
   a. Create GitHub PR via GitHub API (octokit npm package, production
      standard) against the governance repository:
      - Branch name: onboarding/{agentName}/{timestamp}
      - Commits: all candidate files created, all existing files modified
      - PR title: "Agent Onboarding: {agentName} — approved by {approver}"
      - PR body: includes impact delta summary, both HITL tokens,
        eval pass rate, rollback instruction:
        "To roll back: revert this PR. The agent VC expires within 24 hours
        of revocation. No manual governance file cleanup required."
      - PR is created but NOT auto-merged — a human must merge
        (branch protection enforces this)
   b. Store pr_number and pr_url in onboarding_requests
   c. Register new agent in A2A Agent Card registry
   d. Issue VC for new agent via POST /api/agents/credentials/issue
   e. Write Witness entry: { event_type: "agent_onboarded",
        agent_id: new agent's id, pr_number, pr_url,
        files_created, files_modified, eval_pass_rate,
        first_hitl_decided_by, second_hitl_decided_by,
        vc_issued: true, rollback_instruction }
   f. Set status = "onboarded"
   g. Return completed A2A task artifact to the external agent:
      { "type": "text", "text": "Onboarding complete. Your agent has been
        issued a W3C Verifiable Credential and registered in the VDA-MD
        Agent Card registry. PR #{n} contains all governance files.
        Your agent may now submit tasks via A2A." }

   REJECTION at any HITL gate:
   - Set status = "rejected"
   - Write Witness entry: { event_type: "agent_onboarding_rejected",
     rejected_at_phase, rejected_by, reason }
   - No files written, no VC issued, no Agent Card registered
   - Return A2A task failed with error -32002

5. A2A ROUTE FOR ONBOARDING AGENT
   Register POST /a2a/onboarding in the A2A route handler.
   This endpoint sits behind verifyAgentCredential middleware.
   It accepts tasks/send with the Agent Card as the message text
   (JSON-stringified Agent Card in message.parts[0].text).
   All other JSON-RPC methods (tasks/get, tasks/cancel) work as normal
   against the onboarding_requests table status field.

6. ROLLBACK ENDPOINT (server/onboarding/onboardingRollback.ts)
   POST /api/onboarding/{onboarding_id}/rollback
   - Only callable by Compliance Officer (check against owner field —
     implement as a simple API key header check using a
     COMPLIANCE_OFFICER_API_KEY env var)
   - Calls GitHub API to revert the PR (creates a revert PR)
   - Calls DELETE /api/agents/credentials/{agentId} to invalidate VC
     (VC will naturally expire within 24h but explicit revocation
     removes it from the credential store immediately)
   - Removes agent from A2A Agent Card registry
   - Writes Witness entry: { event_type: "agent_offboarded",
     onboarding_id, pr_number, revert_pr_number, rolled_back_by,
     reason }
   - Updates onboarding_requests status to "rolled_back"
   - Returns { status: "rolled_back", revert_pr_url }

CONSTRAINTS:
- octokit npm package for GitHub API calls — npm install @octokit/rest
  (production standard, widely used)
- The Onboarding Agent MUST NOT approve its own onboarding — add a hard
  check in the orchestrator: if agent_card.name === "onboarding-agent"
  return JSON-RPC error -32006 "Self-onboarding not permitted"
- Add error code -32006 to a2aErrors.ts: "Self-onboarding not permitted"
- Sandbox eval uses the candidate SOP.md as the governance file under
  test — pass its content directly to the eval pipeline, do not commit
  candidate files before eval completes
- The GitHub PR is created but never auto-merged — branch protection
  on the governance repo enforces human merge
- Rollback is a revert PR, not a force push — force push is disabled
  by branch protection and must never be circumvented
- All candidate files live in DB (onboarding_requests.candidate_files)
  until PR is created — do not write to filesystem during onboarding
- Impact delta analysis reads from DB only — do not call Claude API
  for the analysis, use deterministic queries and string matching
  against existing governance file content
- The first HITL approver is determined from the RACI resolution in
  the impact delta — if ambiguous, default to Compliance Officer
- Both HITL gates use the existing Add-on 3 POST /hitl/escalate
  endpoint unchanged — onboarding is just another escalation type
- Eval pipeline integration uses the existing /eval-queue/ file-based
  job system from Add-on 2 unchanged
- DeepEval scoring threshold for onboarding eval is 0.95 (same as
  standard governance evals) — do not create a separate threshold
- The Impact Analytics sub-tab aggregates from onboarding_requests
  table only — no separate analytics store needed
- COMPLIANCE_OFFICER_API_KEY is a simple string match in a header
  (X-Compliance-Officer-Key) — document clearly in README that
  enterprise deployments should replace this with Entra ID auth
  via A-Wrapper (out of scope for this implementation)
