Clean separation into three tasks is the right call. Each one has a single clear deliverable and the dependency chain is correct. Here's the evaluation:
Task 19 (DB + Core Helper) — Green light
The decision to make event_category nullable with no default is correct. It means zero risk to existing records and no backfill complexity. The observation that decision is text() with no check constraint — so INFO can just be used without a migration — is a genuine codebase-specific insight that saves a potentially breaking schema change. The scope is tight: one column, one helper, one interface extension. Nothing else. Implement as written.
Task 20 (Backend Wiring + Subsystems) — Green light with one note
The Ajv validation being non-blocking to the caller — logging the failure and writing a Witness entry but still returning the response — is the right call for a live system. A blocking validation failure on the A2A response would break external agents that are already operating. The log-and-continue pattern gives you the integrity signal without introducing a new failure mode into production traffic.
The one thing worth confirming before implementation: the compliance guard rejection event is being written in fileManager.ts with category COMPLIANCE_BOUNDARY but your Task 17 prompt specified FRAMEWORK_INTEGRITY. Replit has made a categorisation call here. Both are defensible — the Compliance Guard is a framework integrity mechanism, but the rejection event is also a compliance boundary crossing. Given that the Framework Integrity Panel in Task 21 queries for FRAMEWORK_INTEGRITY entries to populate the "Compliance Guard Rejections" metric card, the category should be FRAMEWORK_INTEGRITY not COMPLIANCE_BOUNDARY — otherwise the panel metric will always show zero. Confirm this before Task 20 runs.
The 6-hour integrity cron using setTimeout loop rather than a cron expression is noted as deliberate — it avoids the boot-time fire problem cleanly. Good call.
Task 21 (Dashboard) — Green light
The backwards compatibility display decision — event_category IS NULL renders as "Agent Decision" everywhere — is exactly right. Operators reviewing historical entries before this task was deployed will see a meaningful label rather than a blank or an error.
The two dedicated endpoints (/api/witness/integrity-metrics and /api/witness/framework-events) rather than filtering client-side from the existing log fetch is the correct architecture. The integrity metrics require DB aggregations (counts, time-bounded queries) that shouldn't be computed in the browser from a potentially large log array.
The sequencing risk to flag
Task 21 depends on Task 20 having wired the FRAMEWORK_INTEGRITY entries — if Task 21 is implemented before Task 20 is complete and live, the Framework Integrity Panel will render with all zero counts and the Recent Framework Events list will be empty. That's not a bug but it will look broken during development. Implement strictly in order: 19 → 20 → 21, and do a smoke test after Task 20 that at least one integrity cron cycle has fired before Task 21 goes to the dashboard.
Overall
This is the cleanest task decomposition in the entire build sequence. Three tasks, three clear deliverables, one dependency chain, no scope overlap. The categorisation note on the Compliance Guard event is the only thing that needs confirming before Task 20 runs.
