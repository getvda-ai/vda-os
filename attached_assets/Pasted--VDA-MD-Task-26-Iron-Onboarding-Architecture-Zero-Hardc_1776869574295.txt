## 1. The Foundational Principle

**The platform must contain zero business logic.**

Every exception ceiling, every role authority limit, every escalation target, every promotion threshold, every sandbox pass rate — all of it must live in governance files that the platform reads and enforces at runtime. If the file doesn't say it, the platform doesn't know it.

This is not an optimisation. It is the commercial premise of VDA-MD. An Apaleo customer reading the whitepaper must be able to open a governance file and understand exactly what their agents are authorised to do, without reading source code.

## 2. New File Type: EXCEPTION_AUTHORITY.md

This is a new governance file type alongside the existing AGENTS.md / SOP.md / SKILL.md / EXCEPTION.md set.

**Purpose:** Define the standing exception authority for each role band for a specific agent. This is the single source of truth for: what each role can autonomously approve, what the ceiling is for each exception class, what the escalation target is if the ceiling is exceeded, and whether HITL is required.

**File type identifier:** `EXCEPTION_AUTHORITY`

**One file per agent.** Each agent has exactly one EXCEPTION_AUTHORITY.md. It covers all six role bands. Bands with no applicable exceptions use `authority: not_applicable`.

## 3. New Governance File: onboarding-policy.md

This file lives at `companyId=0` (platform sentinel). It defines the thresholds the onboarding orchestrator and dashboard use at runtime.

```yaml
---
file_type: COMPLIANCE
agent_id: onboarding-agent
owner: Compliance Officer
companyId: 0
nist_control: AC-2
---

## VDA-MD Onboarding Policy

### Admission Thresholds

sandbox_pass_threshold: 0.95
# Minimum pass rate required across all sandbox scenarios for Phase 5 to proceed.
# Agents scoring below this threshold fail onboarding and must resubmit.

crawl_agreement_threshold: 0.95
# Minimum per-band agreement rate required to promote from crawl → walk.
# Every required band must independently reach this threshold.

walk_agreement_threshold: 0.95
# Minimum per-band agreement rate required to promote from walk → run.

### File Integrity Thresholds

minimum_clause_counts:
  AGENTS:           { must: 3, must_not: 2, may: 2 }
  SOP:              { must: 3, must_not: 1, may: 1 }
  COMPLIANCE:       { must: 3, must_not: 2, may: 2 }
  SKILL:            { must: 2, must_not: 1, may: 1 }
  EXCEPTION:        { must: 1, must_not: 1, may: 1 }
  EXCEPTION_AUTHORITY: { must: 2, must_not: 1, may: 1 }

### Role Band Classification

front_line_bands:
  - ambassador
  - senior_ambassador
  - hotel_gm

cross_property_bands:
  - regional_gm
  - operations_chief
  - compliance_officer

### Phase Transitions

valid_transitions:
  crawl: walk
  walk: run
```

**Platform changes required:**
- `onboardingOrchestrator.ts`: Read `sandbox_pass_threshold` from this file instead of hardcoding `0.95`
- `dashboard.ts`: Read `FRONT_LINE_BANDS` / `CROSS_PROPERTY_BANDS` / `valid_transitions` from this file
- `fileManager.ts`: Read `minimum_clause_counts` from this file instead of `MINIMUM_CLAUSE_THRESHOLDS`
- `VdaOS.jsx`: Read promotion threshold from this file instead of `0.95` literal

## 8. Onboarding Sequence — The Iron Flow

### Track A: VDA Native Agents

```
SEED SCRIPT (one-time)
  → Creates onboarding_requests with source="vda_native", status="pre_admitted"
  → Creates EXCEPTION_AUTHORITY.md for each agent in File Manager (companyId=0)
  → No A2A pipeline. No HITL. Compliance Officer does not need to admit them.

HOTEL GM (or Regional GM) TRIGGERS ACTIVATION
  POST /api/dashboard/activation/start
  { agentId: "checkout-agent", companyId: 1, initiatedBy: "Hotel GM" }
  → Creates activation_request
  → Reads EXCEPTION_AUTHORITY.md for checkout-agent
  → Extracts ambassador band exception classes
  → Creates exception_acceptance HITL card for ambassador band
  → Sets activationRequest.currentBandStep = "ambassador"

AMBASSADOR REVIEWS EXCEPTION CLASSES
  Card type: exception_acceptance, role_band: ambassador
```

### Crawl → Walk → Run

```
CRAWL (shadow mode, no Apaleo writes)
  Agent makes decisions, logs to Witness Agent
  Each decision surfaced to relevant role band for agree/disagree
  Platform reads crawl_agreement_threshold from onboarding-policy.md
  When ALL required bands independently reach threshold:
  → Hotel GM + CO co-sign crawl completion
  → agent_phases.phase = "walk"

WALK (live, HITL for edge decisions)
  Agent writes to Apaleo
  Decisions within accepted exception_baselines → autonomous
  Decisions at/above ceiling → HITL (card created, routed by EXCEPTION_AUTHORITY.md escalate_to)
  Decisions in MUST NOT override class → CO notification, never auto-approved
  When ALL required bands reach walk_agreement_threshold:
  → Hotel GM + CO co-sign walk completion
  → agent_phases.phase = "run"

RUN (full autonomy within accepted baseline)
  Full autonomy within exception_baselines
  Decisions outside baseline always escalate
  Baseline cannot change without new exception_acceptance cycle
```

## 9. §4 Compliance Guard — EXCEPTION_AUTHORITY.md Protection

The existing `§4 compliance guard` in `fileManager.ts` protects AGENTS.md, SOP.md etc. The same guard must apply to EXCEPTION_AUTHORITY.md with these additional rules:

- Reducing any `ceiling` value is a dilution (requires CO override)
- Changing `authority` from `hitl_required` to `autonomous` is a dilution (requires CO override)
- Removing an `escalate_to` target is a dilution
- Removing any entry from `must_not_override` is a critical dilution (requires CO + Hotel GM co-sign)
- The `minimum_clause_counts` for `EXCEPTION_AUTHORITY` must be enforced (see onboarding-policy.md)
