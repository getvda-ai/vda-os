WHAT THE PLATFORM IS
================================================================================

VDA-MK (Value Driven AI — Management Kit) is a hospitality AI governance
operating system built on top of the Apaleo Property Management System. Its
central thesis is that Markdown is the sole source of truth for all AI agent
behaviour. No business logic for agent decisions is hardcoded in the
application — every threshold, every authority boundary, every compliance rule,
every exception condition lives in a markdown governance file stored in a
PostgreSQL database and loaded at runtime.

The platform is built as a pnpm monorepo with three services running
concurrently:

  Service                        Stack                  Purpose
  ─────────────────────────────────────────────────────────────────────────────
  artifacts/vda-os               React + Vite           Full-stack frontend —
                                                        governance hub, demo,
                                                        file manager, agents
  artifacts/api-server           Node.js + Express +    All agent logic, Apaleo
                                 TypeScript             integration, AI proxy,
                                                        MCP proxy, seed
  artifacts/mockup-sandbox       Vite                   Design prototyping
                                                        environment

THE GOVERNANCE FRAMEWORK (VDA-MD)
================================================================================

The platform is built around VDA-MD — a framework where Markdown files govern
AI agent behaviour. The architecture is described as "Governance-as-Code."


THE FOUR MANDATORY FILE TYPES
-------------------------------

Every agent at every hotel requires exactly three mandatory files. A missing
file causes an immediate ESCALATE decision before any AI or API is invoked
(§2.1 enforcement):

  AGENTS.md (Agent Charter)
    Defines the agent's identity, scope of authority, RACI ownership structure,
    inheritance hierarchy, and which value stream axis it belongs to.

  SOP.md (Standard Operating Procedure)
    Contains all MUST, MUST NOT, and MAY clauses that govern agent decisions —
    the machine-readable rulebook.

  SKILL.md (Skill Manifest)
    Explicitly lists every Apaleo MCP tool the agent is permitted to call,
    including OAuth scope restrictions.

  EXCEPTION.md (Exception Overlay)
    Optional conditional overrides for specific scenarios (e.g., Gold loyalty
    tier late checkout waiver). These extend the SOP without replacing it.

Examples:

THE CANONICAL 29-FILE STACK PER HOTEL
---------------------------------------

Each of the 5 hotels is seeded with the same canonical set of governance files
covering all 8 agents. The total per hotel is approximately 29 files (3
mandatory per agent × 8 agents, plus shared cross-domain and exception files).
These are stored in the governance_files table and served by the File Manager.


THE EIGHT AI AGENTS
================================================================================

Each agent is a standalone API endpoint that follows an identical execution
pipeline:

  1. Governance Pre-flight
     Load AGENTS.md + SOP.md + SKILL.md. If any file missing → immediate
     ESCALATE, no AI called.

  2. Live Data Retrieval
     Call Apaleo via MCP tools (primary) or REST fallback to get current state.

  3. Policy Evaluation
     Send governance text + live data to Claude (Anthropic). Claude must return
     a structured JSON decision and copy the exact policy clause that governed
     its decision.

  4. Action Execution
     Write operations against Apaleo are ONLY executed if the decision is PASS.

  5. Witness Seal
     Every outcome, regardless of decision, is written to the witness_entries
     table.

LIVE APALEO INTEGRATION — HOW IT ACTUALLY WORKS
================================================================================


AUTHENTICATION: OAUTH2 CLIENT CREDENTIALS
-------------------------------------------

The platform authenticates to Apaleo using the OAuth2 Client Credentials Grant:

  Token endpoint:    https://identity.apaleo.com/connect/token
  Credentials:       APALEO_CLIENT_ID and APALEO_CLIENT_SECRET
                     (stored as environment secrets, never in code)
  Token caching:     Tokens are cached in memory. The system checks expiry on
                     every request and refreshes within 30 seconds of expiration.
  Scopes:            availability.read, reservations.read,
                     reservations.manage, finance.read, finance.manage,
                     distribution:reservations.manage, and others.


THE MCP PROXY
--------------

The Model Context Protocol (MCP) is Apaleo's standardised interface for AI
model tool-calling. The platform runs a transparent MCP proxy at /api/mcp that:

  - Accepts JSON-RPC requests (and SSE streaming) from agents
  - Injects the current Apaleo Bearer token into every request automatically
  - Forwards to https://mcp.apaleo.com/mcp
  - Manages Mcp-Session-Id headers for stateful MCP sessions
  - Returns tool results to the calling agent

This means agents call Apaleo tools exactly as an AI model would in a
production deployment — the platform is not simulating this; it is using
Apaleo's actual MCP interface.


THE apaleoRequest FUNCTION
----------------------------

When MCP is unavailable or a direct REST call is needed, agents use a typed
apaleoRequest helper in agents.ts that:

  - Automatically fetches and injects the Bearer token
  - Builds query strings from typed parameter objects
  - Handles 204 No Content responses gracefully
  - Throws descriptive errors with HTTP status and body on failure

THE 7-STEP SCENARIO (LIVE DEMO)
================================================================================

The centrepiece interactive demo runs a complete guest journey through all 7
agents in sequence against live Apaleo data:

  Step 1 — Availability Agent
    Calls GetAvailableUnitGroups against Apaleo — returns real unit count
    (e.g., "49 units available on 2026-04-10")

  Step 2 — Rate Agent
    Calls ListRatePlans — evaluates a 5% discount request (BAR €180 → €171),
    approves autonomously under the 9% policy ceiling

  Step 3 — Reservation Bot
    Calls GetGuestProfile — verifies demo reservation exists in Apaleo,
    confirms booking identity

  Step 4 — Check-In Agent
    Calls CheckIn via MCP — transitions reservation status from Confirmed to
    InHouse in Apaleo live

  Step 5 — Folio Charge Agent
    Calls CreateFolioCharge via MCP — posts an €89 RoomRevenue charge to the
    real folio in Apaleo

  Step 6 — Checkout Agent
    Calls CheckOut via MCP — transitions to CheckedOut; applies Gold loyalty
    exception (late checkout to 13:00, €30 fee waived)

  Step 7 — Revenue Reconciliation
    Calls GetReport or ListFolios — reconciles folio charge vs rate plan
    expectation, seals audit trail

Every step produces a Witness Entry sealed in the database with: agent name,
decision (PASS/FAIL/ESCALATE), reasoning, the exact policy clause that governed
the decision, the governance files consulted, and any Apaleo data used.


THE WITNESS AGENT AUDIT TRAIL
================================================================================

Every agent decision — successful or not — is written to the witness_entries
table. Each entry records:

  agent              Which agent made the decision
  decision           PASS, FAIL, or ESCALATE
  reasoning          Claude's natural-language explanation
  clauseApplied      The verbatim MUST/MAY clause from the governance markdown
                     that governed the outcome
  fileReferenced     The governance file name the clause came from
  filesConsulted     Array of all governance files loaded during evaluation
  actionProposed     What action the agent proposed (e.g., "Execute CheckIn
                     via MCP")
  escalationTarget   Who should be notified if ESCALATE
  apaleoData         JSON blob of the live Apaleo data context used
                     (reservation IDs, folio IDs, rate plan IDs, amounts)
  exceptionApplied   Boolean — whether an EXCEPTION.md overlay changed the
                     outcome

The Witness Agent tab in the UI shows this log in real time, auto-refreshing,
with colour-coded PASS/FAIL/ESCALATE badges.


THE FILE MANAGER
================================================================================

The File Manager is the governance document repository. For each hotel it shows
all 29 canonical markdown files, organised by agent and file type. Users can:

  View and read any file's full markdown content

  Edit files — but every save runs a compliance guard that checks for:
    - Minimum MUST/MUST NOT clause counts (reducing below the seeded baseline
      requires sign-off)
    - Presence of required NIST control references (AC-2, AU-2, etc.)
    - ISO 42001 and SOC 2 keyword preservation
    - Broken cross-references between files

  Sign off on changes — a named accountable role must formally sign governance
  updates

  Version history — every edit creates a new row in governance_file_versions
  with commit message and author

  Regenerate files via the C2MD engine — Claude rewrites the file using
  brand-specific voice and terminology while preserving all compliance clauses

THE COMPLIANCE GUARD (CRITICAL CONTROL):
  If a content edit would reduce the number of MUST clauses, remove a NIST
  reference, or delete an ISO 42001 citation, the API rejects the save with a
  409 Conflict and lists the specific violations. The markdown cannot be
  weakened without a formal named sign-off.


THE C2MD STUDIO (COMPLIANCE-TO-MARKDOWN)
================================================================================

C2MD converts raw regulatory controls into property-specific, brand-voiced
governance markdown. The process:

  1. User selects a target agent and file type (SOP, SKILL, AGENTS)
  2. User provides the source regulatory reference (e.g., "NIST SP 800-53
     AC-2 Account Management")
  3. The system loads the hotel's brand context (extracted from setup wizard)
  4. Claude generates a markdown governance file using citizenM terminology,
     operational context, and authentic brand voice — while embedding all
     required MUST/MUST NOT/MAY normative language and NIST cross-references
  5. The generated file is saved to the File Manager with c2md_generated: true
     in the frontmatter

THE SETUP WIZARD (BRAND CONTEXT INGESTION)
================================================================================

When adding a new hotel property, the wizard:

  1. Takes the property website URL and Apaleo Property ID
  2. Optionally accepts uploaded SOPs, operating manuals, or brand guidelines
     (PDF/DOCX)
  3. Runs a Claude-powered extraction that identifies: guest terminology
     (e.g., "citizen" vs "guest"), staff roles (e.g., "ambassador" vs
     "receptionist"), brand voice characteristics, and property-specific systems
  4. Stores this brand context in the companies table as brandContext
  5. Uses this context in all subsequent C2MD regeneration so governance files
     sound authentically citizenM rather than generic

WHAT MAKES THIS ARCHITECTURALLY SIGNIFICANT
================================================================================

1. ZERO HARDCODED BUSINESS LOGIC IN AGENTS
   Change a MUST clause in a markdown file → the agent's behaviour changes on
   the next request, with no code deployment. This is verified in production:
   adding a new exception to EXCEPTION.md changes the Checkout Agent's decision
   in real time.

2. LIVE APALEO DATA AT EVERY STEP
   The platform does not simulate or mock. Every agent call hits the real Apaleo
   sandbox MCP endpoint. Witness entries contain real Apaleo reservation IDs,
   folio IDs, and rate plan IDs that can be independently verified in the Apaleo
   sandbox portal.

3. COMPLIANCE IMMUTABILITY
   The compliance guard means governance files cannot be weakened by a rogue
   edit — the system enforces that the markdown always maintains its minimum
   compliance posture, with any reduction requiring a formal named sign-off.

4. AUDITABILITY AS A FIRST-CLASS FEATURE
   The Witness Agent trail is not a log file — it is structured relational data
   that includes the exact policy clause, the exact governance file, and the
   exact Apaleo data state at decision time. This is directly consumable by an
   auditor.

5. THE VDA-MD §2.1 ENFORCEMENT RULE
   If any of the three mandatory files (AGENTS.md, SOP.md, SKILL.md) are
   missing for an agent/hotel pair, the system immediately returns ESCALATE
   without calling Claude or Apaleo. The AI cannot operate outside its
   governance envelope.
